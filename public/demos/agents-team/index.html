Une équipe produit d'agents qui livre, teste et se corrige

Six rôles (PM, PO, Tech Lead, dev front, dev back, QA), chacun un modèle choisi selon le prix. Les agents s'échangent des livrables courts, pas des conversations. Le code écrit est exécuté pour de vrai avant le verdict du QA.

Le pipeline

De la demande au code livré

Demande du run : « Ajouter un panier à une boutique en ligne ». Clique sur une étape pour voir ce qu'elle a réellement produit.

QA = KOle côté fautif est refait avec un modèle plus fort, jusqu'à 5 fois, sous un budget de 0,50 $.
Budget

Un plafond de 0,50 $ par run

Le coût est cumulé après chaque réponse, même une réponse vide, qui est facturée. Dépasser le plafond arrête le run et garde les livrables déjà écrits. Les corrections sont aussi limitées à 5.

Itérations

Le code n'est pas bon du premier coup

Chaque tour, les tests sont exécutés puis le QA juge. Un KO renvoie le côté fautif au dev, avec un modèle plus fort.

Preuves

Des tests exécutés, pas relus

Le code du back est écrit sur disque et testé avec unittest dans un environnement sans clé d'API. Des tests rouges l'emportent sur un QA trop indulgent.

Verdict

Le QA a vérifié le code contre 10 critères écrits avant lui

Avant d'écrire une ligne de code, le PO fixe les critères d'acceptation. Le QA relit ensuite le code face à ces critères et aux résultats des tests, puis rend un verdict par côté.

Intégration V1

Se décharger du premier jet, pas de la décision

L'équipe produit un premier jet structuré et testé en quelques minutes pour quelques centimes (de 0,007 $ à 0,08 $ sur mes runs). Un humain décide ce qui est gardé. Choisis une situation.

Bons candidats pour la V1

  • Périmètre petit et clair, logique testable
  • Prototype, spike, outil interne jetable
  • Notes de réunion à transformer en backlog
  • Squelette de code et tests d'un ticket simple

À éviter pour l'instant

  • Code de sécurité, de paiement ou données sensibles
  • Demande floue qu'un humain n'a pas encore cadrée
  • Modification d'un gros code existant : l'équipe travaille dans un dossier vide
  • Tout ce qui touche à la production

Ce que ça m'a appris

Quatre problèmes réels, quatre garde-fous

Un QA qui relit se laisse convaincre

Un modèle juge mal son propre style de code. Le back est donc exécuté et le résultat des tests prime sur l'avis du QA.

Un test peut avoir tort

Un test attendait 5 € de livraison sur un panier de 55 € HT, alors que la règle donnait 0 €. Le QA doit recalculer à la main et dire si c'est le code ou le test qui est faux.

Les modèles à raisonnement répondent vide

Ils dépensent tous leurs tokens à réfléchir. J'ai coupé le raisonnement côté OpenRouter, et l'équipe passe au modèle suivant quand une réponse est vide.

Le périmètre et le coût dérivent

Le PO est limité à 3 stories et le QA ne bloque que sur un critère clairement non rempli. Le budget et le nombre de corrections sont plafonnés.

Et après

Un projet fait pour itérer : vers une V2

Le but est de traiter des situations de plus en plus compliquées au coût le plus bas. Chaque version ajoute une capacité, et le budget tranche : on n'appelle un modèle plus fort que lorsqu'un test ou le QA échoue.
